01 · Core Concepts

Stateless vs Stateful

ก่อนเข้าใจปัญหากับ Load Balancer ต้องเข้าใจก่อนว่า application ของเราเก็บ "สถานะ" ไว้ที่ไหน

🧊
Stateless Application
ทุก request ประมวลผลได้ด้วยตัวเอง ไม่ต้องอาศัยข้อมูลจาก request ก่อนหน้า server ไม่เก็บข้อมูล user ไว้
ง่ายต่อการ scale
🔥
Stateful Application
server เก็บข้อมูล user state ไว้ใน memory หรือ disk (session) request ถัดไปต้องการข้อมูลเดิม
ท้าทายต่อการ scale
🌊
Hybrid (ทั่วไปที่สุด)
Business logic เป็น stateless แต่ใช้ external state store (Redis, DB) เก็บ session ทำให้ scale ได้
Best practice
ลักษณะ Stateless Stateful Hybrid
เก็บ session ที่ไหน ✓ ไม่เก็บ / client side ✗ Server memory ✓ External store (Redis)
Load Balancer ✓ ทุก algorithm ใช้ได้ ✗ ต้องใช้ ip_hash ✓ ทุก algorithm ใช้ได้
Horizontal Scale ✓ เพิ่ม server ได้ทันที ✗ ซับซ้อนมาก ✓ เพิ่มได้ง่าย
Server Crash ✓ ไม่สูญเสียข้อมูล ✗ Session หาย logout ✓ Session ยังอยู่ใน Redis
ตัวอย่าง REST API + JWT, Static sites PHP session default, Classic ASP PHP + Redis session, Node + Redis

02 · The Problem

Session Problem กับ Load Balancer

ปัญหาคลาสสิกที่เจอทุก project เมื่อเพิ่ม Load Balancer เข้าไปใน stateful app แบบเดิม

Session Stickiness Problem — Why Default LB Breaks Sessions
⚠ ปัญหาที่พบบ่อย: นักพัฒนา PHP มักเจอปัญหานี้ตอนเพิ่ม server ครั้งแรก ใช้งานได้ปกติบน single server แต่พอใส่ LB แล้ว user ถูก logout สุ่มเรื่อยๆ เพราะ session_start() ของ PHP เก็บไฟล์ session ไว้บน server นั้นๆ
03 · Solutions

วิธีแก้ปัญหา Session กับ LB

มี 3 วิธีหลักที่ใช้กันในงานจริง แต่ละวิธีมี trade-off ต่างกัน

📌
1. Sticky Session (ip_hash)
Nginx ใช้ IP ของ Client เป็น key hash ให้ Client IP เดิมไปหา Server เดิมเสมอ ง่ายสุด แต่ LB ไม่สมดุลถ้า Client ส่วนใหญ่มา IP เดียวกัน
nginx: ip_hash
🗄️
2. Shared Session Store (Redis)
ทุก server เก็บและอ่าน session จาก Redis ร่วมกัน Server ไหน down ก็ไม่กระทบ Scale ได้อิสระ นี่คือ best practice
Redis + PHP session handler
🔑
3. Stateless Token (JWT)
ไม่เก็บ session บน server เลย ใช้ JWT token ที่ client เก็บ server แค่ verify signature ไม่ต้องการ store ใดๆ
Modern REST API
Solution: Redis Shared Session Store

04 · SSL/TLS

SSL/TLS — ทำให้ HTTP กลายเป็น HTTPS

SSL (Secure Sockets Layer) ถูกแทนที่ด้วย TLS (Transport Layer Security) ที่ปลอดภัยกว่า แต่คนยังคุ้นกับคำว่า SSL ดังนั้นทั้งสองคำหมายถึงสิ่งเดียวกันในการสนทนาทั่วไป

🔐
Encryption
เข้ารหัสข้อมูลระหว่าง client และ server ไม่มีใครดักอ่านได้กลางทาง แม้จะจับ packet ไปก็เป็นแค่ noise
AES-256-GCM
✅
Authentication
Certificate พิสูจน์ตัวตนของ server ว่าคุณกำลังคุยกับ server จริงๆ ไม่ใช่ man-in-the-middle
CA Certificate
🔒
Integrity
ตรวจสอบว่าข้อมูลไม่ถูกแก้ไขระหว่างทาง ด้วย MAC (Message Authentication Code)
HMAC-SHA256
🤝
TLS Handshake
กระบวนการตกลง cipher suite แลกกุญแจ และยืนยัน certificate ก่อนส่งข้อมูลจริง ใช้เวลา 1-2 round trips
TLS 1.3 = 1-RTT

05 · Where to Decrypt

SSL Termination — ถอดรหัสที่ไหน?

SSL Termination คือจุดที่รับ HTTPS และแปลงเป็น HTTP ก่อนส่งต่อ ตำแหน่งที่เลือกมีผลต่อ security, performance และ complexity

SSL Termination Strategies Comparison
🔑 Rule of thumb สำหรับงานจริง:
• Internal network (Docker / Kubernetes) → SSL Termination at LB ก็เพียงพอ network ภายใน trusted
• Compliance (PCI DSS, HIPAA) → End-to-end encryption จำเป็น ต้องใช้ Strategy B หรือ C
• Microservices → มักใช้ mTLS (Mutual TLS) ยืนยันตัวตนทั้งสองฝั่ง
06 · Protocol Deep Dive

TLS Handshake — ขั้นตอนต่อต่อการเข้ารหัส

ก่อนที่ HTTPS จะส่งข้อมูลได้ต้องผ่าน handshake ก่อน ใน TLS 1.3 ใช้แค่ 1 round trip (เร็วกว่า TLS 1.2 ที่ใช้ 2 RTT)

TLS 1.3 Handshake — 1 Round Trip Time (1-RTT)

🛠️ สร้าง Self-Signed Certificate

ssl/generate-certs.shbash 
#!/bin/bash
# ═══════════════════════════════════════════════════════
# สร้าง Self-Signed Certificate สำหรับ development/demo
# ═══════════════════════════════════════════════════════

mkdir -p ssl

# ── สร้าง Private Key + Certificate (x509 self-signed) ─
openssl req -x509 \
  -nodes \              # ไม่เข้ารหัส private key (no passphrase)
  -days 365 \           # cert อายุ 1 ปี
  -newkey rsa:2048 \   # RSA 2048-bit key pair
  -keyout ssl/server.key \   # private key output
  -out    ssl/server.crt \   # certificate output
  -subj "/C=TH/ST=Bangkok/L=Bangkok/O=DevOps-Demo/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"

echo "✅ Certificate created:"
openssl x509 -in ssl/server.crt -text -noout | grep -E "(Subject:|Not Before|Not After|DNS:)"

# ── ดูข้อมูล cert ─────────────────────────────────────
# openssl x509 -in ssl/server.crt -text -noout

07 · Configuration Files

Nginx SSL Configuration

Config ทั้งหมดสำหรับ nginx-lb (HTTPS:443 + HTTP:80 redirect) และ nginx-rp (HTTPS:8443)

nginx-lb/nginx.conf — Load Balancer + SSL Terminationnginx 
# ═══════════════════════════════════════════════════════════
# NGINX LOAD BALANCER with SSL/TLS Termination
# Port 443 (HTTPS) → terminate TLS → Port 80 (HTTP) backends
# Port 80 → redirect to HTTPS
# ═══════════════════════════════════════════════════════════

upstream backend {
    least_conn;
    server app1:80;
    server app2:80;
    server app3:80;
    keepalive 32;
}

# ── HTTP → HTTPS redirect ──────────────────────────────────
server {
    listen      80;
    server_name localhost;

    # Redirect ทุก request ไปยัง HTTPS
    return 301 https://$host$request_uri;
}

# ── HTTPS Load Balancer ────────────────────────────────────
server {
    listen      443 ssl;        # รับ HTTPS
    server_name localhost;

    # ── SSL Certificate ────────────────────────────────────
    ssl_certificate     /etc/nginx/ssl/server.crt;  # public cert
    ssl_certificate_key /etc/nginx/ssl/server.key;  # private key

    # ── TLS Protocol Settings ──────────────────────────────
    ssl_protocols       TLSv1.2 TLSv1.3;          # ห้าม TLS 1.0/1.1
    ssl_ciphers         ECDHE-RSA-AES256-GCM-SHA384:ECDHE-RSA-CHACHA20-POLY1305:ECDHE-RSA-AES128-GCM-SHA256;
    ssl_prefer_server_ciphers on;

    # ── SSL Session Cache (เพิ่ม performance) ──────────────
    ssl_session_cache   shared:SSL:10m;  # 10MB cache
    ssl_session_timeout 10m;
    ssl_session_tickets off;             # disable for perfect forward secrecy

    # ── HSTS Header (force HTTPS) ──────────────────────────
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    # ── Security Headers ───────────────────────────────────
    add_header X-Frame-Options        "SAMEORIGIN" always;
    add_header X-Content-Type-Options  "nosniff" always;
    add_header X-XSS-Protection       "1; mode=block" always;

    # ── Proxy to Load Balanced Backend ─────────────────────
    location / {
        proxy_pass         http://backend;    # HTTP ภายใน (ไม่ต้องเข้ารหัสซ้ำ)
        proxy_http_version 1.1;
        proxy_set_header   Connection        "";
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;    # "https"
        proxy_set_header   X-Forwarded-By    nginx-lb;
    }

    location /lb-status { stub_status on; access_log off; }
}
nginx-rp/nginx.conf — Reverse Proxy + SSL Terminationnginx 
# ═══════════════════════════════════════════════════════════
# NGINX REVERSE PROXY with SSL/TLS
# Port 8443 (HTTPS) → terminate → Port 80 (HTTP) app1
# ═══════════════════════════════════════════════════════════

server {
    listen      443 ssl;
    server_name localhost;

    ssl_certificate     /etc/nginx/ssl/server.crt;
    ssl_certificate_key /etc/nginx/ssl/server.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         ECDHE-RSA-AES256-GCM-SHA384:ECDHE-RSA-AES128-GCM-SHA256;
    ssl_session_cache   shared:SSL:5m;
    ssl_session_timeout 5m;

    add_header Strict-Transport-Security "max-age=31536000" always;
    add_header X-Served-Via             "nginx-rp" always;

    location / {
        proxy_pass         http://app1:80;  # HTTP ภายใน (trusted network)
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_set_header   X-Proxy-By        nginx-rp;
    }

    location /rp-status { stub_status on; access_log off; }
}

# HTTP 8080 → redirect HTTPS 8443
server {
    listen 80;
    return 301 https://$host:8443$request_uri;
}

version: '3.8'

services:

  # ── NGINX Load Balancer + SSL (port 443 + 80→443 redirect) ───
  nginx-lb:
    image: nginx:alpine
    container_name: nginx-lb
    ports:
      - "80:80"    # HTTP → redirect to HTTPS
      - "443:443"  # HTTPS (SSL termination here)
    volumes:
      - ./nginx-lb/nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - ./ssl:/etc/nginx/ssl:ro   # mount SSL certificates
    depends_on: [app1, app2, app3]
    networks: [webnet]

  # ── NGINX Reverse Proxy + SSL (port 8443 + 8080→8443) ────────
  nginx-rp:
    image: nginx:alpine
    container_name: nginx-rp
    ports:
      - "8080:80"   # HTTP redirect
      - "8443:443"  # HTTPS reverse proxy
    volumes:
      - ./nginx-rp/nginx.conf:/etc/nginx/conf.d/default.conf:ro

10 · Production Knowledge

สิ่งที่ควรรู้ในงานจริง

แนวคิดและเทคนิคที่ใช้จริงใน production ที่ทุก DevOps/Backend engineer ควรเข้าใจ

🚦
Rate Limiting
จำกัดจำนวน request จาก IP เดียวกันต่อวินาที ป้องกัน DDoS และ brute-force 
# Nginx rate limiting
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

location /api/ {
    limit_req zone=api burst=20 nodelay;
    proxy_pass http://backend;
}
10r/s = 10 requests/sec, burst=20 อนุญาต spike สั้นๆ
💊
Health Check
Nginx ควร ping backend เป็นระยะ ถ้าล้มให้หยุดส่ง traffic ไป (passive health check ใน Nginx OSS) 
upstream backend {
    server app1:80 max_fails=3 fail_timeout=30s;
    server app2:80 max_fails=3 fail_timeout=30s;
    # ถ้า fail 3 ครั้งใน 30s → marked down
    # หลัง 30s ลอง probe ใหม่อัตโนมัติ
}
Active health check ต้องการ Nginx Plus หรือใช้ third-party module
📋
HSTS (HTTP Strict Transport Security)
บอก browser ว่า "ห้าม HTTP ใช้ได้แค่ HTTPS เท่านั้น" บันทึกไว้ในช่วงเวลาที่กำหนด 
add_header Strict-Transport-Security
  "max-age=31536000; includeSubDomains; preload"
  always;
# max-age=31536000 = 1 ปี
# preload = ขอเข้า Chrome HSTS preload list
⚠ ระวัง: เมื่อเพิ่มแล้วถอดยาก! Test ด้วย max-age=300 ก่อน
⚡
Keepalive & Connection Reuse
การเปิด TCP connection ใหม่ทุก request มี overhead สูง Keepalive ให้ใช้ connection เดิมซ้ำ 
upstream backend {
    keepalive 32; # pool 32 connections
}
location / {
    proxy_http_version 1.1;
    proxy_set_header   Connection "";
    # สำคัญมาก! ลบ Connection: close header
}
ลด latency ได้ 20-50% ในบาง workload
🔏
Perfect Forward Secrecy (PFS)
ถ้า private key รั่วในอนาคต traffic ในอดีตก็ยังถอดรหัสไม่ได้ ใช้ ephemeral key (ECDHE) ทุก session 
# Ciphers ที่รองรับ PFS
ssl_ciphers ECDHE-RSA-AES256-GCM-SHA384
           :ECDHE-RSA-CHACHA20-POLY1305
           :ECDHE-RSA-AES128-GCM-SHA256;
ssl_session_tickets off; # ต้อง off เพื่อ PFS
ECDHE = Elliptic Curve Diffie-Hellman Ephemeral
📦
Gzip Compression
บีบอัด HTTP response ก่อนส่ง ลด bandwidth 60-80% สำหรับ text content (HTML, JSON, CSS) 
gzip              on;
gzip_vary         on;
gzip_proxied      any;
gzip_comp_level   6;   # 1-9, balance speed/ratio
gzip_types        text/plain text/css application/json
                   application/javascript text/xml;
⚠ อย่าใช้กับ binary (images, videos) — ไม่ช่วยอะไร
🗂️
Nginx Caching
Cache response จาก backend ลด load บน app servers สำหรับ content ที่ไม่เปลี่ยนบ่อย 
proxy_cache_path /tmp/nginx_cache levels=1:2
    keys_zone=my_cache:10m max_size=1g inactive=60m;

location /api/static/ {
    proxy_cache            my_cache;
    proxy_cache_valid      200 1h;  # cache 200 responses 1hr
    proxy_cache_use_stale  error timeout;
    add_header             X-Cache-Status $upstream_cache_status;
}
Header X-Cache-Status: HIT/MISS บอกว่า served จาก cache หรือ origin
🏥
Graceful Reload vs Restart
อัพเดท Nginx config โดยไม่ drop connection ที่กำลัง active อยู่ 
# ✓ Graceful reload — ไม่ drop connections
$ nginx -t  # test config ก่อน
$ nginx -s reload

# ✗ Restart — drop active connections
$ systemctl restart nginx

# ใน Docker:
$ docker exec nginx-lb nginx -t
$ docker exec nginx-lb nginx -s reload
Zero-downtime config update — สำคัญมากสำหรับ production
📊
Access Log Format & Analysis
Custom log format เก็บข้อมูลครบสำหรับ debugging และ monitoring 
log_format detailed
  '$remote_addr [$time_local] "$request" $status'
  ' $body_bytes_sent $request_time'
  ' "$http_x_forwarded_for"'
  ' upstream=$upstream_addr';  # สำคัญ! รู้ว่าไปหา server ไหน

access_log /var/log/nginx/access.log detailed;
$upstream_addr = IP:port ของ backend ที่ serve request จริงๆ
🔄
WebSocket Proxying
WebSocket ต้องการ config พิเศษเพราะ upgrade จาก HTTP protocol 
location /ws/ {
    proxy_pass         http://backend;
    proxy_http_version 1.1;
    # สำคัญสำหรับ WebSocket upgrade!
    proxy_set_header   Upgrade    $http_upgrade;
    proxy_set_header   Connection "upgrade";
    proxy_read_timeout 3600s; # long-lived connection
}
⚠ WebSocket = stateful connection → ต้องระวัง LB algorithm (ใช้ ip_hash)
🌐
OSI Model & TCP/IP
Nginx ทำงานที่ Layer 7 (Application) ดู HTTP content ได้ ต่างจาก L4 LB (TCP level)

L4 Load Balancer (HAProxy, AWS NLB): ดู IP+Port เท่านั้น ไม่เปิด HTTP packet เร็วกว่า

L7 Load Balancer (Nginx, AWS ALB): ดู HTTP headers, path, cookies ทำ content-based routing ได้

Nginx upstream ทำงานที่ L7 = รู้ URL path, ทำ sticky session ตาม cookie ได้
🔑
JWT vs Session — เลือกอย่างไร?
ใช้ JWT เมื่อ: Microservices, Mobile API, Third-party integrations, ไม่ต้องการ revoke token ทันที

ใช้ Session + Redis เมื่อ: Web app ที่ต้องการ logout ทันที, เก็บ sensitive data ฝั่ง server, Traditional monolith

ข้อควรระวัง JWT: ถ้า token ถูกขโมยก่อน expire ห้ามใช้ไม่ได้ (ต้องใช้ refresh token + blacklist)
🎯 สรุป Architecture Pattern ที่ดีสำหรับ Production:

🌐 User → CDN/WAF (CloudFlare) → Nginx LB + SSL Term :443 → App1 / App2 / App3 → Redis Sessions + PostgreSQL/MySQL

Key decisions: SSL terminate ที่ LB · Session เก็บใน Redis · App servers เป็น stateless · ใช้ least_conn algorithm · กำหนด max_fails สำหรับ auto-failover · เปิด HSTS · Rate limit ที่ LB
